## Масштабирование и работа с вакансиями

Большая нагрузка, поиск работы, сообщения, фоновые задачи и поэтапное масштабирование описаны отдельно: [SCALABILITY_PLAN.md](SCALABILITY_PLAN.md). Этот документ дополняет базовую модель пользователей и API, а не требует начинать серверную разработку до завершения веб-интерфейса.

## Главный принцип: профиль существует в одном месте

**Идентификатор аккаунта `accountId` неизменяем и выдается сервером после регистрации.**
Профиль (имя, профессия, компания, аватар) принадлежит **аккаунту**, не «другу» и не «чату».

На этапе статического HTML используются следующие коллекции в `app.js`:

```js
state.accounts = {
  "f1": {
    id: "f1",
    name: "Алексей Петров",
    role: "Бурильщик",
    company: "Северное бурение",
    avatarUrl: "assets/avatar-alexey.svg",
    letter: "А",
    skin: "alt1"
  }
};

state.friends = [
  {accountId: "f1", state: "shift", days: 12}
];

state.chats = [
  {
    id: "chat-f1",
    participantAccountId: "f1",
    unread: 2,
    messages: [{id: "message-1", out: false, text: "Привет", time: "09:12"}]
  }
];
```

Здесь `f1` — исключительно стабильный идентификатор **образцового аккаунта**; сервер впоследствии выдаст свои UUID. `chat-f1` — **ID беседы**, он не обязан совпадать с `accountId`.

Функция `avatarByAccountId(accountId)` — единственное место, где определяется аватар аккаунта. В списке друзей, недавних сообщениях, списке чатов, заголовке переписки и анкете используется **одна и та же запись из `state.accounts[accountId]`**. При смене `avatarUrl` в этой записи все экраны должны показывать новый аватар. Не хранить копию URL/имени в `friends`, `chats`, `messages`.

`friendByAccountId(accountId)` объединяет поля профиля и сведения о статусе для отображения, но не создает вторую постоянную копию профиля.

### Как преобразуются старые данные

`migrateSocial(x)` принимает прежний формат версии 1, переносит имя, компанию и аватар в каталог `accounts`, а массивы друзей и чатов преобразует в ссылки `accountId`/`participantAccountId`. Содержимое бесед, история финансов, заметки и другой пользовательский ввод сохраняются. В коде используется версия структуры `2`, импорт резервных копий версии `1` разрешен. Не удалять этот путь без отдельной миграции.

## Серверная модель (базовая версия уже реализована; остальное — план)

Предпочтительный стек при разворачивании: Django + Django REST Framework + PostgreSQL; WebSocket — через Django Channels **после** реализации API и авторизации. Это направление, не обязательство использовать конкретную библиотеку.

| Таблица | Основные поля | Назначение |
|---|---|---|
| `accounts` | `id UUID PK`, `display_name`, `avatar_key`, `profession`, `organization`, `created_at` | Единый профиль пользователя |
| `friendships` | `id`, `requester_id FK`, `recipient_id FK`, `status`, `created_at` | Подтверждённые дружбы/заявки. Уникальная неупорядоченная пара |
| `conversations` | `id UUID PK`, `kind`, `created_at` | Личная или групповая беседа |
| `conversation_members` | `conversation_id FK`, `account_id FK`, `last_read_message_id` | Участие и счётчик непрочитанного |
| `messages` | `id UUID PK`, `conversation_id FK`, `sender_account_id FK`, `body`, `created_at` | Сообщения отдельно от записей участников |
| `shift_periods` | `account_id FK`, `start_date`, `end_date`, `status` | История вахт и обратные отсчёты |
| `payments` | `account_id FK`, `date`, `type`, `amount`, `comment` | Выплаты; доступ по правам |
| `employer_reviews` | `account_id FK`, `organization_id`, `salary_rating`, `living_rating`, `management_rating`, `schedule_rating`, `comment` | Отзывы и четыре критерия |
| `privacy_settings` | `account_id PK/FK`, `status_visibility`, `calendar_visibility`, `finance_visibility`, `rating_visibility`, `comment_visibility`, ... | Права просмотра по отдельным полям |
| `notifications` | `id`, `recipient_account_id`, `kind`, `read_at`, `payload` | Уведомления и счётчики |

`organization_id` при необходимости указывает на отдельную таблицу работодателей. Фотографии/аватары — файлы в медиа-хранилище или объектном хранилище, а не base64-строки в таблице.

**Собственный `accountId` определяется текущей серверной сессией**, а не выбирается клиентом произвольно. Для чата другому человеку используется его `accountId`, для открытия существующей беседы — `conversationId`.

## Контракт API (план, версия /api/v1)

Пример минимального чтения:

```http
GET /api/v1/me
GET /api/v1/friends
GET /api/v1/accounts/{accountId}
GET /api/v1/conversations
GET /api/v1/conversations/{conversationId}/messages
```

Пример ответа для списка бесед:

```json
{
  "accounts": [
    {"id":"6ac...","name":"Алексей","avatarUrl":"/media/avatars/6ac.webp"}
  ],
  "conversations": [
    {"id":"9bd...","participantAccountId":"6ac...","unread":2,"lastMessage":"Привет!"}
  ]
}
```

Беседа **ссылается** на собеседника; данные аватара/имени являются карточкой аккаунта из нормализованного словаря. Для групповых бесед следует использовать массив `memberAccountIds` и отдельный аватар группы.

Операции будущего API:

```http
POST /api/v1/friend-requests
POST /api/v1/friend-requests/{requestId}/accept
DELETE /api/v1/friends/{accountId}
POST /api/v1/conversations/direct
POST /api/v1/conversations/{conversationId}/messages
PATCH /api/v1/me/profile
POST /api/v1/me/avatar
PATCH /api/v1/me/privacy
GET /api/v1/accounts/{accountId}/shift
GET /api/v1/accounts/{accountId}/payments
GET /api/v1/accounts/{accountId}/employer-review
```

`POST /conversations/direct` принимает `otherAccountId` и атомарно возвращает **существующую или созданную** беседу. Это предотвращает создание двух разных чатов с одним собеседником при повторном нажатии.

После загрузки списка с сервера нормализовать ответы по `accountsById[accountId]`. Переписка, друзья, профиль и статус используют один и тот же источник данных. Обновление профиля или URL аватара инвалидирует кеш записи аккаунта и обновляет все связанные виды.

## Переход от HTML-прототипа к серверу

1. Сохранить внешний пользовательский UI `index.html`, `styles.css`, `friends.css` и логику компонентов.
2. Выделить слой API/репозитория данных из `app.js`. Заменить текущий `seed/load/persist` на HTTP-запросы для социальной части, финансов и графика. В будущем это будут асинхронные действия с индикаторами загрузки и обработкой ошибок.
3. Ввести авторизацию и серверный `accountId` пользователя. Не выдавать доступ к данным по присланному произвольному `accountId`.
4. Перенести данные в PostgreSQL с миграциями. Для пользовательского импорта сохранить сопоставление прежних локальных идентификаторов и выданных сервером UUID; не допускать дублирования связей.
5. Сначала реализовать реальные запросы дружбы и личные беседы через HTTP; после этого подключить WebSocket и push.
6. При обновлении аватара сохранить `avatar_key` в `accounts`; клиент получит новый `avatarUrl` в данных аккаунта. **Не** обновлять имя и фото вручную во всех чатах.
7. Подключить синхронизацию истории вахт, выплат, заметок и оценок с полноценным доступом по настройкам.

## Важные правила безопасности и приватности

- Сервер проверяет аутентификацию, дружбу и настройки видимости **на каждом запросе** к чужому профилю, календарю, финансам и отзыву.
- Финансы — только владельцу по умолчанию. Настройки «Друзьям» и «Всем» применяются лишь после явного действия владельца; нельзя доверять скрытым элементам интерфейса как защите.
- Чтение сообщений допускается только участникам беседы; отправитель берётся из сессии, не из тела запроса.
- Не включать закрытые суммы и личные даты в JSON ответа, если доступа нет, даже если UI их не показывает.
- Не публиковать токены, пароли и серверные секреты в репозитории GitHub Pages.
- Для аватаров на сервере проверять тип, размер, содержимое файла; пользовательские SVG безопаснее не принимать. Публиковать проверенные PNG/WebP/JPEG с уникальными ключами.
- При размещении фронтенда на GitHub Pages и API на другом домене заранее настроить корректные CORS/CSRF и HTTPS; хранение долгоживущих токенов в `localStorage` не использовать.
- Для перехода в офлайн-режим позднее предусмотреть кеш и очередь операций, но разрешение конфликтов остаётся на сервере.

## Что не следует ломать при доработках

- Ссылка `accountId` в друзьях и `participantAccountId` в беседах.
- Общая функция рендеринга аватаров `avatarByAccountId`.
- Перенос старых сохранений версии 1 в новую структуру.
- Независимые ID бесед/сообщений.
- Закрытые по умолчанию финансы и отдельные настройки доступа к оценкам.

UI намеренно содержит только пользовательские элементы. Технические пояснения и ограничения текущей реализации должны оставаться в документации, а не засорять экраны.
