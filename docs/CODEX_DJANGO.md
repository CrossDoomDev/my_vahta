# Codex: правила развития Django backend и Android/frontend

1. Репозиторий `CrossDoomDev/my_vahta` — **единый источник кода**. Django приложение `backend/` с `backend/manage.py` и PostgreSQL. Не переходить самовольно обратно на Node.js/Fastify. `requirements.txt` находится в корне.
2. Не удалять работающие `index.html`, `app.js`, `styles.css`, `friends.css`, `data/`, `assets/`. Сохранять текущие UI/локальные данные до полной миграции. GitHub Pages пока используется только для просмотра прототипа; локальный Django отдаёт тот же UI и REST API.
3. API `/api/v1/` разрабатывается и тестируется сначала локально. Текущий `backend/core/` — доменный модуль; разделение на Django apps (accounts/shifts/finances/social/messaging/employers) делать по мере роста, **с миграциями без потери данных**.
4. Одна серверная запись `Shift(user,start,end,vacation)` — источник дат для календаря, финансов, таймеров. Продление вахты пересчитывает все зависимые данные. Для финансов сумма — фактически внесённые суммы по датам внутри периода включительно, включая 2–3 месяца.
5. `User` внутренний ID + `Profile.id` UUID для внешнего API. Никогда не считать `f1`, `demo-*` или локальных друзей реальными аккаунтами. При входе экран друзей использует серверный API; без входа демонстрирует учебный прототип. Заявки `FriendRequest` требуют авторизации, серверных проверок и согласия второго пользователя.
6. API приватных данных всегда фильтрует владельца на **сервере**, а не CSS/JS. Личные финансы по умолчанию скрыты. Поиск профиля по имени — только при `discoverable=True`; телефонные контакты не собирать без отдельного разрешения, безопасного сопоставления и документов.
7. Серверные секреты, `.env`, токены, дампы БД, реальные контакты и личные файлы не коммитить. Android — будущий клиент Kotlin; на нём токен хранить в защищённом хранилище. В тестовом браузере токен лишь в `sessionStorage`.
8. `backend-client.js` и `MV_APP_BRIDGE` пока поддерживают **только ручную синхронизацию** графика, выплат и заметок по явному подтверждению. Оффлайн-данные и backend не должны автоматически перезаписывать друг друга. Использовать `revision` и `409`; перед фоновой синхронизацией отдельно спроектировать разрешение конфликтов.
9. Для каждого изменения модели: новая Django migration, `makemigrations --check --dry-run`, тесты c PostgreSQL в GitHub Actions. Не использовать `migrate --run-syncdb`, не удалять миграции и не сбрасывать базу пользователя ради удобства разработки.
10. Проверять безопасность: нельзя удалять чужие записи, принимать чужие заявки, читать переписку без дружбы, искать неподтверждённый номер, импортировать демоданные автоматически, использовать DEBUG/runserver на публичном сервере.
11. Инструкции: [LOCAL_DJANGO_SETUP.md](LOCAL_DJANGO_SETUP.md), [API.md](API.md), [CODEX_FRIENDS_ANDROID.md](CODEX_FRIENDS_ANDROID.md). Прежние планы в `SERVER_ARCHITECTURE.md` и `SCALABILITY_PLAN.md` актуализировать по мере реализации.
