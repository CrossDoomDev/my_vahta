# План масштабирования «Моей вахты»

> **Обновление: октябрь 2026.** Django + PostgreSQL API уже добавлены в `backend/` вместе с миграциями. См. [локальный запуск](LOCAL_DJANGO_SETUP.md), [API v1](API.md), [правила для Codex](CODEX_DJANGO.md). Старый HTML-прототип всё ещё использует локальные демо-данные, а реальная синхронизация дат, выплат и заметок пока ручная. Все неупомянутые API в этом документе — целевые, не обязательно уже реализованные.

**Назначение:** проектные решения на случай роста от нескольких сотен до большого числа активных пользователей. Этот документ — задание и ограничения для будущей работы Codex. **Серверная основа реализована:** Django + PostgreSQL, API и миграции добавлены; развёртывание на ноутбуке — следующий практический шаг.

Связанный документ: [SERVER_ARCHITECTURE.md](SERVER_ARCHITECTURE.md) — базовые модели аккаунтов, друзей и переписки. При реализации настоящего backend оба документа использовать совместно.

## 1. Продукт: не просто календарь, а площадка для вахтовиков

Нужно проектировать расширяемые домены:
- **Аккаунты и профили:** профессия, компетенции, опыт, регион, предпочтения работы, контакты, аватар, отдельная приватность каждого поля.
- **Личный помощник:** календарь и история вахт, отпуск, заметки, выплаты и статистика.
- **Социальная сеть:** друзья/заявки, статусы, личные и групповые чаты, уведомления, блокировки и жалобы.
- **Работодатели и организации:** единый справочник компаний, филиалов, вакансий/площадок, оценки по четырём критериям, отзывы и модерация.
- **Работа и вакансии:** публикация вакансий, фильтры, избранное, отклики, взаимодействие соискателя и работодателя, сохранённые поиски, оповещения.
- **Коммуникационные контакты:** явно выбранные пользователем каналы связи и их видимость. Возможность указать ссылку на внешнюю платформу не означает существование официальной интеграции с ней.

Границы модулей должны быть понятны до создания моделей БД, но UI остаётся единым.

## 2. Архитектурное решение: масштабируемый модульный монолит

**Выбор:** Python + Django + Django REST Framework + PostgreSQL. Запускать как один проект Django, разбитый на независимые Django apps с собственными моделями, сервисами, API и тестами.

Предлагаемые пакеты:
```
backend/
  config/               # settings, URLs, ASGI, logging
  apps/
    accounts/            # единый accountId, профиль, вход, контакты
    social/              # дружба, блокировки, жалобы
    shifts/              # графики, статус, календарь
    finances/            # выплаты, видимость
    employers/           # компании, площадки, оценки, модерация
    jobs/                # вакансии, поиск, отклики, сохранённые фильтры
    messaging/           # беседы, участники, сообщения
    notifications/       # события и уведомления
    notes/               # личные заметки
    media/               # учёт метаданных загрузок
  api/v1/
  tests/
frontend/
  index.html
  styles.css
  app.js
```
Это **целевая логическая структура**, а не команда сейчас переносить файлы, удалять существующий HTML или начинать Django-проект.

**Ключевой принцип:** UI обращается к интерфейсу работы с данными (data access / API adapter); сам UI не должен быть намертво связан с `localStorage`, конкретным VPS, PostgreSQL или ответом одного endpoint. Пока backend нет, адаптер пользуется локальной реализацией; позже — API.

Не вводить микросервисы, Kubernetes, брокеры событий, шардирование или несколько баз «на всякий случай». Извлекать отдельный сервис только при доказанной технической потребности.

## 3. Идентификаторы и данные

- Неизменяемые `accountId`, `conversationId`, `messageId`, `organizationId`, `vacancyId`, `applicationId`; рекомендуемый серверный формат UUID. Не использовать имя/номер телефона/ID чата как ID аккаунта.
- `accounts` — единственный источник имени и аватара. `friendships`, `conversation_members`, `messages`, `applications` ссылаются на аккаунт. UI уже использует `avatarByAccountId(accountId)`.
- Не дублировать профиль в чатах. Повторяющиеся поля в API допустимы лишь как read-only проекции с управляемым обновлением кеша.
- Денежные суммы в PostgreSQL — `NUMERIC` либо целое количество минимальных денежных единиц; никаких вычислений финансов в `float`.
- Время событий и сообщений — `created_at` с часовым поясом (UTC внутри БД), с конвертацией при показе пользователю; вахтовые календарные даты — отдельные `DATE` в нужном часовом контексте.
- Профессии, работодатели, площадки и вакансии — отдельные сущности и связи; названия организаций не должны быть уникальными ID.
- Проектировать миграции без потери данных, с обратной совместимостью и поэтапными изменениями схемы (expand → migrate → contract). Миграцию существующего формата `app.js` v1→v2 не удалять.

## 4. Сообщения при большой аудитории

- PostgreSQL — **каноническое постоянное хранилище** сообщений; Redis никогда не единственная копия переписки.
- Каждое сообщение: уникальный ID, `conversation_id`, `sender_account_id`, время создания, содержимое/метаданные, при необходимости `client_message_id` для защиты от повторной отправки.
- Список бесед: последняя активность и счётчики непрочитанного доступны без чтения всей истории; членство — отдельная таблица.
- Загрузка истории — **курсорная пагинация** (например, `before_message_id`), максимум N сообщений за запрос. Никакого `SELECT *` всей переписки.
- Индексы для типовых запросов (например, сообщения: `(conversation_id, created_at DESC, id DESC)`; участники: `(account_id, conversation_id)`). Проверять реальные планы через `EXPLAIN ANALYZE`.
- HTTP API должен работать независимо от WebSocket: получение истории, отправка, идемпотентность и статус прочтения — отдельно от мгновенной доставки.
- WebSocket при необходимости: Django Channels/ASGI + Redis channel layer. При потере соединения клиент подтягивает пропущенные сообщения через API; Redis не является архивом событий.
- Для тяжёлых уведомлений, медиа, почты и индексации — фоновая очередь; задачи повторяемые/идемпотентные, ошибки и повторные попытки учитываются.
- Предусмотреть блокировки, жалобы, ограничение частоты сообщений и антиспам до открытия регистрации для широкой аудитории.
- Групповые чаты: отдельная `conversation_members`, роли участников, правила присоединения/выхода; `participantAccountId` текущего HTML отражает **только личные** беседы.

## 5. Вакансии, поиск и отзывы

**Вакансии** — самостоятельный домен, не разновидность сообщений. В будущем:
`employers`, `employer_memberships`, `vacancies`, `vacancy_locations`, `vacancy_requirements`, `applications`, `saved_searches`, `job_alerts`.

Разграничение ролей: соискатель, представитель работодателя, модератор, владелец платформы. Работодатель должен пройти отдельное подтверждение полномочий; рядовой пользователь не может присвоить себе чужую компанию.

Поиск начать с индексов и полнотекстового поиска PostgreSQL, а отдельный поисковый движок рассматривать только по метрикам. Фильтры по специальности, региону, графику, опыту, оплате; результаты — пагинация, сортировка, кеширование безопасных публичных запросов.

Отзывы об организациях — потенциальный источник конфликтов: история правок, жалобы, модерация, защита от накруток, отделение пользовательского мнения от проверенной информации. Никогда не показывать работодателю приватные выплаты/календарь работника без отдельно предоставленного разрешения.

Контакты и внешние мессенджеры могут быть атрибутами профиля со своими уровнями видимости. Не считать, что hh.ru поддерживает интеграцию с «Моей вахтой», пока нет официального соглашения и документации.

## 6. Медиа и статический контент

Аватары, фотографии компаний, вложения в чаты/отзывы хранить в файловом или S3-совместимом хранилище, а в PostgreSQL — ключ, тип, размер, владелец, версии и метаданные доступа.

Раздавать статические изображения через nginx/CDN или эквивалент с кешем. Для приватных вложений — авторизованная выдача/короткоживущие подписанные ссылки. Проверять форматы, объём, содержимое, квоты; нормализовать изображения; исключить исполнение HTML/SVG от незнакомых пользователей.

Не хранить фотографии в `accounts` строками base64 и не перекладывать большую нагрузку медиа на процессы Django.

## 7. Масштабирование инфраструктуры по фактической нагрузке

| Этап | Размещение | Что добавляем и почему |
|---|---|---|
| **Сейчас** | Только статический HTML и тестовые данные | Полное согласование UX и функций. Сервер не создаём |
| **Первые пользователи** | Один VPS: reverse proxy + Django + PostgreSQL, бэкапы; отдельная директория медиа или объектное хранилище | Невысокая стоимость, единая кодовая база, наблюдаемость |
| **Рост активности** | По необходимости выносим PostgreSQL, добавляем Redis, ASGI/WebSocket, фоновые workers и отдельное файловое хранилище | Устраняем конкретные узкие места |
| **Высокая нагрузка** | Несколько экземпляров stateless Django за балансировщиком, пул соединений, отдельная БД, возможные реплики чтения, CDN | Масштабирование без изменения бизнес-логики |
| **Очень высокая нагрузка** | Точечное секционирование больших таблиц, оптимизация поиска, изоляция самых нагруженных подсистем при доказанной необходимости | Не преждевременные микросервисы, а измеряемые решения |

**Количество зарегистрированных пользователей ≠ одновременная нагрузка.** Мощность рассчитывать после тестов: одновременные подключения, запросы в секунду, сообщений/сек, объёмы вложений, пиковые часы. Не обещать конкретных лимитов одного VPS без измерений.

Таблицы сообщений и уведомлений можно секционировать позже по времени или другой подходящей стратегии, если обычные индексы и аппаратные ресурсы перестанут справляться. PostgreSQL предоставляет встроенное секционирование; оно не всегда ускоряет запросы, поэтому включать его после профилирования.

## 8. Проверка доступа и безопасность

- Авторизация и права **на сервере**; запрошенный ID пользователя не даёт права прочесть закрытые данные.
- Каждый запрос к чужим финансам, календарю, статусу, отзывам и контактам проходит проверку видимости и дружбы. Финансы по умолчанию видит только владелец.
- Приватные поля исключаются из API-ответа (не просто скрываются CSS). Отдельные права на работодателя, модератора, друга, заблокированного пользователя.
- rate limiting, предотвращение массового перебора аккаунтов и вакансий, защита от спама, блокировки, аудит административных изменений.
- HTTPS, безопасные cookies/CSRF там, где применимо, защита секретов, регулярные бэкапы и тестовые восстановления.
- Для проекта с персональными данными граждан РФ **перед публичным запуском** проверить требования 152-ФЗ, в том числе локализацию баз данных на территории РФ, требования к документации и уведомлению уполномоченного органа. Это вопрос юридической подготовки, а не только выбора VPS.
- Предусмотреть удаление аккаунта, экспорт данных и регламент хранения переписки/логов; сроки и правовые основания определить перед запуском.

## 9. Производительность и контроль роста

С первого серверного релиза ввести: структурированные логи, метрики времени ответа (p50/p95/p99), ошибки, медленные SQL-запросы, загрузку CPU/RAM, длину очереди workers, доступность API, число активных WebSocket, скорость поступления сообщений, объём БД и медиа.

Нагрузочные сценарии включают:
- сотни/тысячи пользователей читают вакансии, выполняют фильтры и открывают анкеты;
- активные переписки: отправка, просмотр истории, reconnect, дубль сообщения, смена аватара;
- массовые уведомления о новых вакансиях без блокировки HTTP;
- скачивание аватаров/фотографий без расходования Django workers;
- проверка закрытых финансов при прямом запросе к API чужого пользователя.

До появления пользователей устанавливать «целевые бюджеты» для API и медиа, но корректировать после реальных замеров. Масштабирование запускать по метрикам, не по числу зарегистрированных аккаунтов.

## 10. Правила Codex в процессе разработки веб-версии

1. **Не создавать Django/Redis/PostgreSQL и не покупать VPS до отдельного решения.**
2. Можно делать экраны и сценарии для вакансий, отзывов, контактов, друзей, сообщений, уведомлений.
3. Предпочитать стабильные идентификаторы и централизованное состояние; не копировать аватар и имя в каждую переписку.
4. Для будущих вызовов сервера выделять простые функции-договоры, например `getAccount(accountId)`, `listVacancies(filters, cursor)`, `listMessages(conversationId, cursor)`, `sendMessage(conversationId, payload)`, `updatePrivacy(patch)`. Пока реализации локальные.
5. Для интерфейса списков предусмотреть загрузку частями, состояния «загружается / пусто / ошибка», быстрый поиск и мобильную адаптацию.
6. Не показывать в UI технические надписи о тестовых данных или прототипе; эти сведения — только для репозитория и документации.
7. Не обещать реальный публичный обмен сообщениями, когда сеть и backend ещё отсутствуют.
8. Изменение серверной схемы в будущем не должно требовать переписывания всех экранов.
